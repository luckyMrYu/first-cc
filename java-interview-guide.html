二、Java 基础 · 高频知识点

Q1：== 和 equals 的区别？
== 比较的是引用（内存地址），基本类型比较值。equals() 默认行为同 ==，但 String、Integer 等类重写了 equals() 比较内容/值。
重写 equals 必须重写 hashCode，否则 HashMap/HashSet 无法正常工作。
Q2：HashMap 的 put 流程？（必考）
① 计算 key 的 hash 值（高 16 位 ^ 低 16 位，扰动函数）
② 根据 hash 定位桶位置 i = (n-1) & hash
③ 桶为空 → 直接放入
④ 桶不为空 → 判断首节点 key 是否相同（hash 相等且 equals 为 true）
⑤ 如果是红黑树 → putTreeVal
⑥ 否则遍历链表，尾插法插入；key 相同则覆盖 value
⑦ 插入后判断是否需要扩容（size > threshold）或树化（链表长度 ≥ 8 且数组长度 ≥ 64）
Q3：HashMap 为什么容量是 2 的幂？
① hash % n 等价于 hash & (n-1)，位运算更高效
② 扩容时，元素要么在原位置，要么在 原位置 + 旧容量，不需要重新计算 hash
③ 2 的幂 - 1 的二进制全是 1，hash 分布更均匀
Q4：ArrayList 和 LinkedList 的区别？
ArrayList：动态数组，随机访问 O(1)，尾部插入均摊 O(1)，中间插入 O(n)。扩容为原来的 1.5 倍。
LinkedList：双向链表，随机访问 O(n)，头尾插入 O(1)。额外存储前后指针，内存开销更大。
实际开发：绝大多数场景用 ArrayList，CPU 缓存友好。
Q5：ConcurrentHashMap 如何实现线程安全？（必考）
JDK 7：分段锁（Segment 数组），每个 Segment 继承 ReentrantLock，并发度 = Segment 个数（默认 16）。
JDK 8：取消 Segment，采用 Node 数组 + 链表 + 红黑树，使用 CAS + synchronized 锁住链表头节点，锁粒度更细。size() 使用 baseCount + CounterCell[] 类似 LongAdder 的方式统计。
Q6：String 为什么是不可变的？
① String 类声明为 final，不可继承
② 内部 char[] value（JDK 9+ 改为 byte[]）声明为 private final
③ 所有修改操作都返回新对象
好处：字符串常量池、线程安全、hashCode 可缓存（只需计算一次）、安全性（作为 HashMap key、类加载参数）。
Q7：Java 8 有哪些新特性？
① Lambda 表达式 & Stream API
② 接口默认方法（default）和静态方法
③ Optional 类（避免 NPE）
④ 新的日期时间 API（LocalDate/LocalTime/LocalDateTime）
⑤ 方法引用（::）
⑥ CompletableFuture
⑦ HashMap 底层优化（链表 → 红黑树）

三、并发编程 · 高频知识点

Q1：线程池的 7 个核心参数？（必考）
ThreadPoolExecutor 构造函数：
① corePoolSize：核心线程数（即使空闲也不回收）
② maximumPoolSize：最大线程数
③ keepAliveTime：非核心线程空闲存活时间
④ unit：时间单位
⑤ workQueue：阻塞队列（LinkedBlockingQueue / ArrayBlockingQueue / SynchronousQueue）
⑥ threadFactory：线程工厂（可设置线程名）
⑦ handler：拒绝策略（AbortPolicy / CallerRunsPolicy / DiscardPolicy / DiscardOldestPolicy）

任务提交流程：核心线程未满 → 创建核心线程；核心满了 → 入队列；队列满了 → 创建非核心线程直到 max；都满了 → 执行拒绝策略。
为什么不用 Executors：FixedThreadPool / SingleThread 队列长度为 Integer.MAX_VALUE（OOM 风险）；CachedThreadPool 最大线程数为 Integer.MAX_VALUE（OOM 风险）。
Q2：synchronized 的原理？锁升级过程？
原理：基于 Monitor（监视器锁）。同步代码块用 monitorenter/monitorexit 字节码指令；同步方法用 ACC_SYNCHRONIZED 标志。
锁升级（只能升级不能降级）：
① 无锁：没有竞争
② 偏向锁：Mark Word 记录线程 ID，单线程访问无竞争（JDK 15 默认关闭）
③ 轻量级锁：出现竞争，膨胀为轻量级锁，Mark Word 指向 Monitor，线程自旋等待
④ 重量级锁：自旋失败，升级为重量级锁，线程阻塞（操作系统层面，涉及用户态/内核态切换）
Q3：volatile 的作用和原理？
① 可见性：修改变量后立即写回主内存，读变量时从主内存读取（通过 lock 前缀指令锁定缓存行）
② 禁止指令重排：通过内存屏障（Memory Barrier）保证有序性
③ 不保证原子性：i++ 不是原子操作，需要用 AtomicInteger
经典应用：DCL 单例模式中 instance 必须加 volatile，防止指令重排导致拿到未初始化对象。
Q4：ThreadLocal 原理？内存泄漏？
原理：每个 Thread 对象内部有一个 ThreadLocalMap，key 是 ThreadLocal 的弱引用，value 是强引用。调用 threadLocal.set(value) 实际是存入当前线程的 map。
内存泄漏：如果 ThreadLocal 外部强引用被置 null，GC 后 key 被回收，但 value 还被 ThreadLocalMap.Entry 强引用。如果线程不结束（线程池），value 永远无法回收。
解决：用完后一定要调用 remove()。
Q5：AQS 原理？ReentrantLock 怎么用？
AQS（AbstractQueuedSynchronizer） 核心：
① state 变量（volatile int）表示同步状态
② FIFO 的 CLH 变体双向队列，存放等待线程
③ 基于 CAS 修改 state

ReentrantLock：state=0 表示未锁定，state>0 表示重入次数。公平锁先检查队列有没有等待线程；非公平锁直接 CAS 抢锁，失败才入队。
对比 synchronized：ReentrantLock 可中断（lockInterruptibly）、可超时（tryLock）、可公平、支持多个 Condition。
Q6：CAS 原理？ABA 问题？
CAS（Compare And Swap）：比较并交换，包含三个操作数：内存位置 V、预期值 A、新值 B。只有 V == A 时才把 V 更新为 B。这是一条 CPU 原子指令（cmpxchg）。
ABA 问题：V 从 A 变成 B 又变回 A，CAS 认为没变过。解决方案：AtomicStampedReference（带版本号）或 AtomicMarkableReference。
CAS 缺点：自旋开销（长时间失败会空转 CPU）、只能保证一个变量的原子操作。
Q7：CountDownLatch / CyclicBarrier / Semaphore 区别？
CountDownLatch：计数器，await() 等待计数器归零，一次性的（不能重置）。场景：主线程等待多个子线程完成。
CyclicBarrier：循环屏障，所有线程到达屏障后一起执行，可重置（reset()）。场景：多线程分阶段计算。
Semaphore：信号量，控制同时访问的线程数（acquire/release）。场景：限流、数据库连接池。

四、JVM · 高频知识点

Q1：JVM 内存结构？（必考）
① 程序计数器：线程私有，记录当前线程执行的字节码行号
② 虚拟机栈：线程私有，每个方法调用创建一个栈帧（局部变量表、操作数栈、动态链接、返回地址）
③ 本地方法栈：为 Native 方法服务
④ 堆：线程共享，对象实例分配的地方，GC 主要区域。分年轻代（Eden + S0 + S1，比例 8:1:1）和老年代
⑤ 方法区（元空间，JDK 8+）：存储类信息、常量、静态变量、JIT 编译代码。JDK 8 后改用本地内存实现（MetaSpace）
Q2：对象的创建过程？
① 类加载检查：检查类是否已加载
② 分配内存：指针碰撞（堆规整）或空闲列表（堆不规整），并发用 CAS + 失败重试或 TLAB（线程本地分配缓冲区）
③ 初始化零值：成员变量赋默认值（int=0, object=null）
④ 设置对象头：Mark Word（hashcode、GC 分代年龄、锁状态等）+ 类型指针（指向方法区的类元数据）
⑤ 执行 <init>：构造方法
Q3：类加载机制？双亲委派？如何打破？
类加载过程：加载 → 验证 → 准备 → 解析 → 初始化
双亲委派：ClassLoader 收到请求先委派父加载器，父加载器无法加载才自己加载。BootStrap → Extension → Application → Custom。
好处：避免类重复加载、保护核心 API 不被篡改。
打破方式：
① 重写 loadClass() 方法
② 线程上下文类加载器（SPI 机制，如 JDBC、JNDI）
③ OSGi 热部署
Q4：垃圾回收算法？
① 标记-清除：标记存活对象，清除未标记的。缺点：内存碎片
② 标记-复制：将存活对象复制到另一块区域。缺点：浪费一半空间。适合年轻代（对象存活率低）
③ 标记-整理：标记后将存活对象向一端移动。适合老年代
④ 分代收集：年轻代用复制算法，老年代用标记-清除/整理
Q5：G1 垃圾收集器原理？
G1（Garbage First）将堆划分为多个大小相等的 Region（默认 2048 个），每个 Region 可以是 Eden、Survivor、Old 或 Humongous（大对象）。
核心特点：
① 可预测的停顿时间（-XX:MaxGCPauseMillis）
② 优先回收垃圾最多的 Region（Garbage First 由来）
③ 使用 RSet（Remembered Set） 记录跨 Region 引用
④ 垃圾识别使用 SATB（Snapshot-At-The-Beginning） 算法
回收过程：初始标记（STW，借助 Minor GC）→ 并发标记 → 最终标记（STW，处理 RSet）→ 筛选回收（STW，选择 Region 复制回收）
Q6：GC Roots 有哪些？
① 虚拟机栈中引用的对象（局部变量）
② 方法区中静态属性引用的对象
③ 方法区中常量引用的对象
④ 本地方法栈中 JNI 引用的对象
⑤ 被同步锁（synchronized）持有的对象
⑥ JVM 内部引用（基本类型的 Class 对象、系统类加载器、异常对象等）
Q7：如何排查 OOM？
① 启动参数加 -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/path
② 使用 MAT（Memory Analyzer Tool）或 JProfiler 分析 heap dump
③ 查看 GC Roots 引用链，找到泄漏对象的创建位置
④ 常见原因：集合类未清理、ThreadLocal 未 remove、大对象未关闭、连接未释放

五、Spring · 高频知识点

Q1：Spring IoC 原理？
IoC（控制反转）：对象的创建和依赖关系由 Spring 容器管理，而不是手动 new。
DI（依赖注入） 是 IoC 的实现方式：
① 解析配置文件/注解，生成 BeanDefinition
② BeanFactory 根据 BeanDefinition 创建 Bean 实例
③ 通过反射注入依赖属性
BeanFactory：Spring 底层容器，延迟初始化。ApplicationContext：BeanFactory 的子接口，启动时预创建单例 Bean，支持国际化、事件发布等高级功能。
Q2：Spring Bean 生命周期？（必考）
① 实例化（Instantiation）：反射创建对象
② 属性注入（Populate）：注入依赖
③ Aware 回调：BeanNameAware、BeanFactoryAware、ApplicationContextAware
④ BeanPostProcessor.postProcessBeforeInitialization()
⑤ 初始化：@PostConstruct → InitializingBean.afterPropertiesSet() → init-method
⑥ BeanPostProcessor.postProcessAfterInitialization()（AOP 代理在此创建）
⑦ 使用
⑧ 销毁：@PreDestroy → DisposableBean.destroy() → destroy-method
Q3：Spring AOP 原理？
AOP（面向切面编程） 将横切关注点（日志、事务、权限）与业务逻辑分离。
实现原理：
① JDK 动态代理：目标类实现了接口，使用 java.lang.reflect.Proxy
② CGLIB 代理：目标类没有实现接口，通过生成子类（不能代理 final 类和方法）
核心概念：切面（Aspect）、切点（Pointcut）、通知（Advice：Before/After/Around/AfterReturning/AfterThrowing）、连接点（JoinPoint）
Spring Boot 2.x 默认使用 CGLIB。
Q4：Spring 如何解决循环依赖？（三级缓存）
循环依赖：A 依赖 B，B 依赖 A。
解决方式：三级缓存
① singletonObjects：存放完全初始化好的 Bean
② earlySingletonObjects：存放早期暴露的 Bean（未完全初始化）
③ singletonFactories：存放 ObjectFactory（用于创建早期 Bean）
流程：A 创建 → 实例化 → 放入三级缓存 → 注入 B → B 创建 → 注入 A（从三级缓存获取，如果有 AOP 则创建代理放入二级缓存）→ B 完成 → A 完成。
不能解决：构造器注入的循环依赖（对象还没创建）、prototype 作用域。
Q5：Spring 事务失效的场景？
① 方法不是 public
② 自调用：同一个类中 A 方法调 B 方法（不经过代理）
③ 异常被 try-catch 吞了
④ 数据库不支持事务（如 MySQL MyISAM）
⑤ 传播行为设置错误（如 NOT_SUPPORTED）
⑥ 没有被 Spring 管理（类没加 @Service）
⑦ 多线程调用（不同线程不同连接）
解决自调用：注入自身、AopContext.currentProxy()、拆分类。
Q6：Spring Boot 自动配置原理？
① @SpringBootApplication 包含 @EnableAutoConfiguration
② @EnableAutoConfiguration 通过 @Import(AutoConfigurationImportSelector.class) 导入自动配置类
③ 读取 META-INF/spring.factories（Spring Boot 2.x）或 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports（Spring Boot 3.x）
④ 根据 @Conditional 条件注解（如 @ConditionalOnClass）决定是否生效
⑤ 生效的配置类注册 Bean 到容器

六、MySQL · 高频知识点

Q1：B+ 树索引结构？为什么不用 B 树？
B+ 树特点：
① 非叶子节点只存 key，不存数据；叶子节点存数据
② 叶子节点用双向链表连接，范围查询高效
③ 所有查询都到叶子节点，查询性能稳定 O(log n)
对比 B 树：B 树每个节点都存数据，无法做高效范围查询；B+ 树非叶子节点能存更多 key，树更矮，磁盘 IO 更少。
Q2：聚簇索引 vs 非聚簇索引？回表？覆盖索引？
聚簇索引：叶子节点直接存整行数据。InnoDB 主键索引就是聚簇索引，一张表只有一个。
非聚簇索引（二级索引）：叶子节点存的是主键值。
回表：通过二级索引找到主键后，再去聚簇索引查完整数据。一次回表 = 一次额外 IO。
覆盖索引：查询的字段都被索引覆盖，不需要回表。EXPLAIN 中 Extra: Using index。
Q3：索引失效的场景？
① 不满足最左前缀原则（联合索引 (a,b,c)，查询没用 a）
② 对索引列使用函数/运算（WHERE YEAR(create_time) = 2026）
③ 隐式类型转换（varchar 列用数字查）
④ LIKE 以通配符开头（LIKE '%abc'）
⑤ OR 条件中有非索引列
⑥ NOT IN / != / <> 在某些情况下
⑦ 优化器判断全表扫描更快（数据量小 / 选择性差）
Q4：MVCC 原理？
MVCC（多版本并发控制） 实现读写不冲突。
核心组件：
① 隐藏列：每行数据有 DB_TRX_ID（最后修改的事务 ID）和 DB_ROLL_PTR（回滚指针）
② undo log 版本链：每次修改生成旧版本，通过 roll_ptr 串联
③ ReadView（读视图）：事务快照读时生成，包含活跃事务列表
  - m_ids：生成 ReadView 时活跃（未提交）的事务 ID 列表
  - min_trx_id：活跃事务中最小 ID
  - max_trx_id：生成 ReadView 时系统应该给下一个分配的事务 ID
  - creator_trx_id：创建该 ReadView 的事务 ID
可见性规则：版本链中从上往下找，找到第一个对当前事务可见的版本。
RC 隔离级别每次 SELECT 都生成新的 ReadView；RR 隔离级别只在第一次 SELECT 生成。
Q5：MySQL 锁机制？
按粒度：
① 全局锁：锁整个数据库实例（FLUSH TABLES WITH READ LOCK，用于备份）
② 表级锁：表锁、元数据锁（MDL）、意向锁（IS/IX）
③ 行级锁：Record Lock（记录锁）、Gap Lock（间隙锁）、Next-Key Lock（临键锁 = 记录锁 + 间隙锁）
按类型：共享锁（S 锁，读）、排他锁（X 锁，写）
间隙锁：防止幻读，锁定索引间隙。SELECT ... FOR UPDATE 在 RR 级别会加 Next-Key Lock。
Q6：redo log、undo log、binlog 区别？
redo log（InnoDB 引擎层）：
① 物理日志，记录"在某个数据页上做了什么修改"
② 循环写，WAL（Write-Ahead Logging）技术
③ 用于崩溃恢复（crash-safe）

undo log（InnoDB 引擎层）：
① 逻辑日志，记录数据的反向操作
② 用于事务回滚和 MVCC

binlog（MySQL Server 层）：
① 逻辑日志，记录所有 DDL 和 DML
② 追加写，不会覆盖
③ 用于主从复制和数据恢复（mysqlbinlog）

两阶段提交：保证 redo log 和 binlog 一致性。prepare → 写 binlog → commit。
Q7：慢 SQL 如何排查和优化？
① 开启慢查询日志：slow_query_log = ON，long_query_time = 1
② 使用 EXPLAIN 分析执行计划：
  - type：system > const > eq_ref > ref > range > index > ALL（至少到 range）
  - key：实际使用的索引
  - rows：扫描行数
  - Extra：Using filesort（排序优化）、Using temporary（临时表优化）
③ 优化索引、改写 SQL、避免回表、分页优化（延迟关联）
④ 大数据量：分库分表（ShardingSphere）

七、Redis · 高频知识点

Q1：Redis 数据类型及底层结构？
① String：SDS（Simple Dynamic String）
② List：quicklist = ziplist + 双向链表（Redis 7+ 改为 listpack）
③ Hash：ziplist / listpack（数据少）→ hashtable（数据多）
④ Set：intset（全是整数）→ hashtable
⑤ ZSet：ziplist / listpack（数据少）→ skiplist + hashtable（数据多）
⑥ 特殊类型：Bitmap、HyperLogLog、GEO、Stream
Q2：Redis 为什么快？为什么单线程还能高并发？
① 纯内存操作
② 单线程避免了多线程的上下文切换和锁竞争
③ IO 多路复用（epoll）：一个线程处理多个连接
④ 高效的数据结构：跳表、压缩列表等
注意：Redis 6.0 引入多线程，但仅用于网络 IO 的读写，命令执行仍然是单线程。
Q3：缓存穿透、击穿、雪崩？解决方案？（必考）
缓存穿透（查不存在的数据）：
→ 布隆过滤器拦截不存在的 key
→ 缓存空值（设置短 TTL）

缓存击穿（热点 key 过期，大量并发打到 DB）：
→ 互斥锁（SETNX）：只允许一个线程查 DB 并回写
→ 逻辑过期：不设置实际 TTL，value 中存过期时间，异步更新

缓存雪崩（大量 key 同时过期 / Redis 宕机）：
→ TTL 加随机值，避免同时过期
→ 多级缓存：本地缓存（Caffeine）+ Redis + DB
→ Redis 高可用：哨兵 / Cluster
Q4：Redis 持久化方案？
RDB（快照）：
① fork 子进程，利用 COW（Copy-On-Write）生成快照
② 保存到 dump.rdb
③ 优点：恢复快、文件紧凑。缺点：可能丢失最后一次快照后的数据

AOF（追加文件）：
① 记录每条写命令到 appendonly.aof
② 刷盘策略：always / everysec / no
③ AOF 重写：压缩文件，去除冗余命令
④ 优点：数据更安全。缺点：文件大、恢复慢

混合持久化（Redis 4.0+）：AOF 重写时前半段是 RDB 格式，后半段是 AOF 增量。兼顾恢复速度和数据安全。
Q5：Redis 分布式锁如何实现？有什么问题？
基本实现：SET key value NX EX seconds
问题：
① 锁过期但业务没执行完 → Redisson 看门狗自动续期
② Redis 主从切换导致锁丢失 → RedLock 算法（多节点加锁，多数成功才算成功，但争议较大）
③ 非持有者释放锁 → value 用 UUID + 线程 ID，释放时用 Lua 脚本保证原子性

Redisson 优势：自动续期、可重入、支持读写锁、公平锁。
Q6：Redis 集群方案？
主从复制：读写分离，主写从读。全量同步（第一次/断太久）+ 增量同步（offset）。
哨兵模式（Sentinel）：监控主从节点，主挂了自动故障转移（选举新主）。
Cluster 模式（官方推荐）：
① 数据分片：16384 个哈希槽分配到不同节点
② 去中心化：节点间 Gossip 协议通信
③ 自动故障转移
④ key 的槽 = CRC16(key) % 16384
⑤ 支持 {hashtag} 保证相关 key 在同一槽（用于 multi-key 操作）

八、分布式 · 高频知识点

Q1：CAP 定理和 BASE 理论？
CAP：分布式系统最多同时满足两个：
① C（Consistency）一致性：所有节点数据一致
② A（Availability）可用性：每个请求都能得到响应
③ P（Partition tolerance）分区容错：网络分区时系统仍能运行
实际 P 必须保证，所以选 CP 或 AP：
CP：ZooKeeper、Etcd（保证一致性，可能拒绝服务）
AP：Eureka、Nacos（默认 AP，可切换 CP）

BASE：CAP 的延伸，核心是最终一致性
① BA（Basically Available）基本可用
② S（Soft state）软状态
③ E（Eventually consistent）最终一致性
Q2：分布式事务方案？
① 2PC（两阶段提交）：prepare + commit/rollback。缺点：同步阻塞、单点故障
② 3PC：增加 canCommit 阶段 + 超时机制，降低阻塞
③ TCC：Try-Confirm-Cancel，业务层面实现。性能高但侵入性强
④ 本地消息表：事务操作 + 写消息到本地表，定时任务发送到 MQ，消费方保证幂等
⑤ Saga：长事务拆成多个本地短事务，每个有补偿操作。失败时反向补偿
⑥ 最大努力通知：事务发起方完成本地事务后通知各方，失败重试。适用于对一致性要求低的场景

Seata 支持 AT、TCC、Saga、XA 四种模式。AT 模式最常用（无侵入）。
Q3：雪花算法（Snowflake）原理？
64 位 Long 型 ID = 1 位符号 + 41 位时间戳（毫秒级，约 69 年）+ 10 位工作机器 ID（支持 1024 个节点）+ 12 位序列号（每毫秒 4096 个 ID）
优点：全局唯一、趋势递增、高性能、不依赖数据库
问题：时钟回拨会导致 ID 重复。解决方案：等待、记录上次同步时间。
Q4：限流算法有哪些？
① 固定窗口：每个时间窗口内允许 N 个请求。缺点：窗口交界处流量翻倍
② 滑动窗口：将窗口细分，更平滑。Sentinel 使用
③ 漏桶算法：以固定速率处理请求，平滑突发流量。不适合处理突发流量
④ 令牌桶算法：以固定速率生成令牌，有令牌才能处理。允许一定程度的突发流量。Guava RateLimiter 使用

九、计算机网络 · 高频知识点

Q1：TCP 三次握手？为什么三次？
① 客户端 → SYN（seq=x）→ 服务端
② 服务端 → SYN+ACK（seq=y, ack=x+1）→ 客户端
③ 客户端 → ACK（ack=y+1）→ 服务端

为什么三次：防止历史连接导致资源浪费。如果两次握手，过期的 SYN 到达服务端，服务端会建立错误连接并分配资源。三次握手客户端可以确认自己的 SYN 是否被正确接收。
为什么不能两次：无法确认客户端的接收能力，可能导致单方建立连接。
Q2：TCP 四次挥手？为什么 TIME_WAIT 持续 2MSL？
① 客户端 → FIN → 服务端（客户端进入 FIN_WAIT_1）
② 服务端 → ACK（服务端 CLOSE_WAIT，客户端 FIN_WAIT_2）
③ 服务端 → FIN（服务端 LAST_ACK）
④ 客户端 → ACK（客户端 TIME_WAIT，等待 2MSL）

为什么四次：TCP 全双工，每个方向需要单独关闭。服务端收到 FIN 可能还有数据要发送。
为什么 TIME_WAIT 持续 2MSL（MSL = Maximum Segment Lifetime，约 60s）：
① 确保最后一个 ACK 能到达服务端（如果丢了，服务端重发 FIN）
② 让网络中该连接的旧报文消失，避免新连接收到旧数据
Q3：HTTPS 握手过程？
① 客户端发送支持的加密算法列表 + 随机数 ClientRandom
② 服务端选择加密算法 + 返回证书 + 随机数 ServerRandom
③ 客户端验证证书（CA 签名）→ 生成预主密钥 Pre-Master → 用服务端公钥加密发送
④ 服务端用私钥解密得到 Pre-Master
⑤ 双方用 ClientRandom + ServerRandom + Pre-Master 生成会话密钥
⑥ 后续通信使用会话密钥（对称加密）

混合加密：非对称加密交换密钥 + 对称加密传输数据。兼顾安全和性能。
Q4：HTTP 1.0 / 1.1 / 2.0 / 3.0 区别？
HTTP 1.0：每次请求都新建 TCP 连接
HTTP 1.1：持久连接（keep-alive）、管道化（队头阻塞）、Host 头（虚拟主机）、分块传输
HTTP 2.0：二进制分帧、多路复用（一个 TCP 上并行多个请求）、头部压缩（HPACK）、服务器推送
HTTP 3.0：基于 QUIC（UDP）、解决 TCP 队头阻塞、0-RTT 连接建立、内置加密
Q5：从输入 URL 到页面展示的全过程？（综合高频题）
① DNS 解析：域名 → IP（浏览器缓存 → 系统缓存 → 路由器 → ISP DNS → 根域名服务器）
② TCP 连接：三次握手
③ TLS 握手（HTTPS）：协商加密算法、交换证书、生成会话密钥
④ 发送 HTTP 请求：GET/POST，包含请求头、Cookie 等
⑤ 服务器处理：负载均衡 → Web 服务器 → 应用服务器 → 数据库
⑥ 返回响应：HTML、CSS、JS、图片等
⑦ 浏览器渲染：
  - 解析 HTML → DOM 树
  - 解析 CSS → CSSOM 树
  - 合并 DOM + CSSOM → Render 树
  - Layout（布局）→ 计算元素位置和大小
  - Paint（绘制）→ 像素绘制
  - Composite（合成）→ 分层合成最终画面
⑧ TCP 四次挥手（连接关闭）

十、消息队列 · 高频知识点

Q1：为什么用 MQ？有什么缺点？
优点：
① 解耦：生产者消费者不直接依赖
② 异步：耗时操作异步处理，减少响应时间
③ 削峰：突发流量先入队列，慢慢处理

缺点：
① 系统复杂度增加（一致性、重复消费、顺序等问题）
② 系统可用性降低（MQ 挂了怎么办）
③ 数据一致性问题
Q2：Kafka 架构？为什么快？
架构：
① Broker：Kafka 服务器
② Topic：消息主题
③ Partition：分区，一个 Topic 多个 Partition 分布在不同 Broker
④ Producer：生产者
⑤ Consumer：消费者，属于某个 Consumer Group
⑥ Offset：消费者在 Partition 中的消费位置

为什么快：
① 顺序写磁盘：追加写入，比随机写快几个数量级
② 零拷贝（sendfile）：数据从磁盘直接到网卡，不经过用户空间
③ 页缓存（PageCache）：利用 OS 缓存
④ 批量发送 + 压缩
⑤ Partition 并行处理
Q3：如何保证消息不丢失？
生产者端：
① 开启确认机制：Kafka acks=all；RabbitMQ 开启 publisher confirm
② 发送失败重试

Broker 端：
① Kafka：replication.factor >= 3，min.insync.replicas >= 2
② RabbitMQ：镜像队列 / 仲裁队列

消费者端：
① 关闭自动提交 offset
② 处理完业务后再手动提交
Q4：如何保证消息不重复消费（幂等性）？
① 唯一 ID：每条消息生成唯一 msgId
② 数据库唯一约束：msgId 作为唯一索引，插入成功才算消费成功
③ Redis SETNX：用 msgId 做 key，消费前先 SETNX
④ 乐观锁：更新操作带上版本号
⑤ 业务幂等：比如扣款，用 余额 = 余额 - 金额 而不是 余额 = 原值

十一、AI + 大模型 · 2026 新增考点（Java 生态全覆盖）

Q1：什么是 LLM？基本概念？
LLM（Large Language Model）大语言模型，基于 Transformer 架构，通过海量文本预训练的神经网络。
核心概念：
① Token：文本被切分的最小单位（可能是词、子词或字符）
② Prompt：输入给模型的提示文本
③ Temperature：控制输出随机性，0 = 确定性，1 = 随机性
④ Top-P：从概率前 P% 的 token 中采样
⑤ Context Window：模型能处理的最大 token 数
Q2：什么是 RAG？架构是怎样的？
RAG（Retrieval-Augmented Generation）检索增强生成，解决 LLM 知识过期、幻觉问题。
架构：
① 离线索引：文档 → 切块（Chunk）→ Embedding 模型 → 向量数据库
② 在线检索：用户提问 → 向量化 → 在向量库中检索 Top-K 相关文档
③ 增强生成：将检索到的文档 + 用户问题组装成 Prompt → LLM 生成答案

Java 实现：Spring AI + Milvus / Elasticsearch 8.x
Q3：什么是 AI Agent？和 RAG 有什么区别？
AI Agent智能体 = LLM + 工具使用 + 规划 + 记忆。
ReAct 模式：Reasoning（推理）→ Action（行动）→ Observation（观察）循环。
和 RAG 区别：
① RAG 是被动检索 + 生成
② Agent 可以主动规划、调用工具、多步推理
③ Agent 可以包含 RAG 作为其工具之一
Q4：什么是 Function Calling / Tool Use？
LLM 本身只能生成文本，Function Calling 让 LLM 能够调用外部工具（API、数据库、搜索引擎等）。
流程：
① 开发者定义可用工具（函数签名、参数描述）
② LLM 根据用户意图决定调用哪个工具
③ LLM 返回工具名 + 参数
④ 开发者执行工具，将结果返回给 LLM
⑤ LLM 基于工具结果生成最终回答
Q5：什么是 MCP 协议？
MCP（Model Context Protocol）是 Anthropic 提出的开放标准，让 LLM 以统一方式连接外部数据源和工具。
架构：Host（宿主应用）→ Client（协议客户端）→ Server（工具/数据提供方）
核心能力：Tools（工具）、Resources（资源）、Prompts（提示模板）、Sampling（采样）
Java 生态：Spring AI 已支持 MCP，可以直接集成各种 MCP Server。
Q6：Prompt Engineering 有哪些技巧？
① 角色设定："你是一位资深 Java 工程师..."
② Few-shot：提供几个输入-输出示例
③ CoT（Chain of Thought）：让模型"一步步思考"
④ 约束条件：明确输出格式、长度限制
⑤ 分隔符：用 XML 标签或 Markdown 清晰分隔不同部分
⑥ 自我一致性：多次采样取多数投票结果

Q17：Fine-tuning（微调）是什么？什么时候用？
Fine-tuning：在预训练模型基础上，用特定领域数据继续训练，让模型适应特定任务。
vs Prompt Engineering：
• Prompt：不改模型，通过提示词引导。快速、便宜、可解释
• Fine-tune：改模型权重。效果更稳定、可减小 prompt 长度、但贵且需数据

什么时候用 Fine-tuning：
① 输出格式需要非常稳定（如总是输出 JSON）
② 领域术语 / 风格特殊（如法律、医疗）
③ Prompt 已经很长但仍不够好

主流微调方法：
• LoRA / QLoRA：低秩适配，训练成本低（消费级显卡可跑）
• Full Fine-tuning：全参数微调，效果最好但贵
• P-Tuning v2：只训练前缀参数

Java 生态：一般用 Python 训练，部署后用 Java 调用（HTTP / gRPC）。阿里 ModelScope、Hugging Face 是模型库。

Q1：如何设计一个秒杀系统？
核心目标：高并发、防超卖、防刷
方案：
① 前端：按钮置灰、验证码、静态资源 CDN
② 网关层：限流（令牌桶）、IP 黑名单、用户鉴权
③ 服务层：
  - Redis 预扣库存：DECR 操作，库存 < 0 则返回失败
  - 发送 MQ 消息异步下单
④ 下单层：消费者从 MQ 取消息 → 数据库扣库存（乐观锁 / 行锁）→ 创建订单
⑤ 订单超时：延迟队列取消未支付订单，释放库存

防超卖：Redis 原子操作 + 数据库乐观锁双重保障
Q2：如何设计一个短链接系统？
需求：长链接 → 短链接（如 bit.ly/abc123），访问短链跳转长链
方案：
① 生成短码：
  - 自增 ID + Base62 编码（简单，但可预测）
  - 雪花 ID + Base62（唯一但不连续）
  - MD5 + 取前 6 位 + 冲突处理
② 存储：短码 → 长链的 KV 存储（MySQL / Redis）
③ 跳转：301（永久）或 302（临时，可统计访问次数）
④ 缓存：热门短链放 Redis，减少 DB 查询
Q3：如何设计一个 Feed 流系统？
两种模式：
① 推模式（写扩散）：用户发布 → 推到所有粉丝的收件箱。写入量大，但读取快。适合大 V 少的场景
② 拉模式（读扩散）：读取时聚合关注的人的时间线。读取量大，但写入简单。适合关注少的场景
③ 推拉结合：普通用户推模式，大 V 拉模式（粉丝太多不推）

存储：Timeline 数据放 Redis（ZSet，score 为时间戳），历史数据放 HBase / Cassandra
